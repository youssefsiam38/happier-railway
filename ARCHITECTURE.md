# Architecture

```
 phone / desktop / web app         computers running agents (happier CLI + daemon)
            \                                   /
             \  HTTPS + WebSocket (/v1/updates)/
              v                               v
        +---------------------------------------------+
        | Railway service "happier"  (public, :3005)  |
        |   railway-start (bash, PID 1)               |
        |     -> run-server -> happier-server (light) |
        |   SQLite + files + master secret: /data     |  <- Railway volume
        +---------------------------------------------+
```

One service, one volume. No database service: the relay's light flavour uses SQLite on the volume.

## Service

| setting | value |
|---|---|
| image | `ghcr.io/youssefsiam38/happier-railway:<version>@sha256:…` (FROM `happierdev/relay-server:stable-<sha>@sha256:…`) |
| port | `PORT=3005` (public domain target port 3005) |
| health check | `/health` |
| volume | `/data` |
| public URL | `HAPPIER_PUBLIC_SERVER_URL` and `HAPPIER_WEBAPP_URL` = `https://${{RAILWAY_PUBLIC_DOMAIN}}` (embedded in QR codes and deep links) |
| token secret | `HANDY_MASTER_SECRET`, generated by Railway |
| proxy trust | `HAPPIER_SERVER_TRUST_PROXY=100.64.0.0/10` — Railway's edge connects from that range, so rate limits key on the real client IP |

The relay stores only what clients send it. Session content, messages and settings are end-to-end encrypted by the
apps; the server cannot read them.

## Why a wrapper

The upstream image is used unmodified. The wrapper adds one start script for two things the stock image cannot do on
Railway:

1. **Volume ownership.** Railway mounts volumes owned by root; the image runs as the non-root `happier` user. The
   script starts as root, `chown`s `/data` when needed, and re-executes itself as `happier` with `setpriv`.
2. **Sign-up lock.** Happier accounts are device keys: any client that signs a challenge at `POST /v1/auth` gets an
   account while anonymous sign-up is enabled (the upstream default). Upstream's only switch is
   `AUTH_ANONYMOUS_SIGNUP_ENABLED`, read per request from the process environment. Closing it from the start would
   leave the deployer no way to create their own account; GitHub/OIDC-only sign-up needs an OAuth app and is not
   one-click. So the script:
   - counts rows in the `Account` table of `/data/happier-server-light.sqlite`;
   - below `SIGNUP_ACCOUNT_LIMIT` (default 1): starts the server with sign-up open and re-counts every 2 s; when the
     limit is reached it stops the server and starts it again with `AUTH_ANONYMOUS_SIGNUP_ENABLED=false`;
   - at or above the limit: execs the server with sign-up closed.

   With sign-up closed, `POST /v1/auth` returns `403 signup-disabled` for unknown keys and still signs in existing
   ones; terminal pairing (`/v1/auth/request` + `/v1/auth/response`) and device linking attach to existing accounts,
   so they keep working.

   The light server runs its shutdown handlers on SIGTERM but its process does not exit afterwards, so the script
   SIGKILLs it after a 5 s grace period (the database is already closed by then). The restart takes about 8 s.

Other variables: `SIGNUP_ACCOUNT_LIMIT=0` disables the lock; an explicit `AUTH_ANONYMOUS_SIGNUP_ENABLED` disables the
lock and is passed through; a non-SQLite `HAPPIER_DB_PROVIDER` with the lock on refuses to start rather than leave
sign-up open. `HAPPIER_SENTRY_USE_CENTRAL_DSN=0` is set in the image so crash reports do not go to the Happier
project's Sentry unless the deployer opts in.
